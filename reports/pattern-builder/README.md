# Pattern Builder — 작업 장부

> river 목표(2026-09-18): 회사 부품·토큰·디자인 문법을 기반으로, 웹·앱·S/W·서비스 유형별로 패턴을 조합하는 빌더.
> 레거시 화면은 레거시 가이드로 두고, 새 화면은 신규 가이드 부품으로 조합한다. 1차 범위는 **HTML/CSS 까지**(개발 소스 구조 연동은 뒤로).
>
> ⛔ **레거시 서비스 패턴은 정본에 합치지 않는다** (river 결정 2026-09-18). 이미 운영 중이고 레거시
> 가이드라인이 적용된 서비스(모두앱 등)에 최신 부품을 억지로 끼워 넣거나, 그 서비스 패턴을 최신
> 가이드에 병합하면 안 된다. 서비스별 자료는 `reports/pattern-builder/profiles/<매체>-<서비스>/` 에 따로 보관한다.

## 구성

| 조각 | 위치 | 역할 |
|---|---|---|
| 빌더 사이트(별도) | `builder/index.html` + `builder.css` + `builder.js` | 가이드 사이트와 분리된 독립 웹사이트(river 결정 2026-09-18). 배포본(ui-library/dist)·registry·design 매니페스트를 상대경로로 읽는다. 조립 → 미리보기 → HTML 내보내기 |
| 패턴 목록(정본) | `registry/patterns/builder/catalog.json` | 빌더가 읽는 패턴 정의. 레거시 판독 → 검증 → 승인된 것만 `verified/approved`. (`registry/patterns/*.json` 바로 아래는 Gate 의 패턴 사양 자리라 하위 폴더에 둔다) |
| 요청 접수함 | `reports/pattern-builder/requests/` | 빌더 "새 패턴 요청" 이 만든 `pattern-request-*.json` 을 두는 곳 |
| 레거시 판독표 | `reports/pattern-builder/inventory/<service>/` | 레거시 화면을 읽어 정리한 "어느 서비스 · 어떤 화면 유형 · 어떤 부품" 표와 원자료 |
| 레거시 서비스 전용 규칙 | `reports/pattern-builder/profiles/<매체>-<서비스>/` | 그 서비스에서만 쓰는 규칙·부품. **정본과 분리** |

## 흐름

1. **레거시 읽기** 🤖 figma-inspector — river 가 준 Figma 파일을 읽어 판독표 작성
2. **패턴 등록** ⭐ — 판독표 근거로 `builder/catalog.json` 에 layout 작성(부품은 dist id 만)
   ▸ 검문소 🤖 component-verifier — 정본 부품·토큰만 썼는지, 레거시 원본과 대응이 맞는지
3. **빌더** — 목록에서 패턴 고르기 → 부품 옵션 → HTML 내보내기
   ▸ 검문소 🔎 — 내보낸 코드가 배포본 부품·토큰만 쓰는지 + 렌더 확인
4. **새 패턴 요청** — 빌더 요청서 → ⭐ 디자인 문법에 맞춰 제안 → 2번 검문소 → 목록에 등장. 기존 부품으로 안 되면 부품 신설은 needs-decision(H6②)

## 규칙(빌더가 지키는 것)

- 부품·변형·크기 축은 dist manifest 에서만 읽는다. 빌더 안에서 새 이름·새 부품을 만들지 않는다.
- 오버레이(모달·바텀시트) 와 부속(드롭다운·GNB 하위메뉴) 은 화면 안 배치 대상이 아니라 팔레트에서 뺀다(manifest placement 기준).
- 색·간격·글꼴은 tokens.css / typography.css 의 토큰·클래스만 쓴다(HEX 없음).
- 내보낸 HTML 은 `./s1-ui/` 아래에 dist 를 그대로 둔다는 전제(tokens.css · typography.css · s1-ui.css · s1-ui.auto.js).

- 화면 틀(프레임) — **PC 1920×1080 · 모바일 360×780**(river 결정 2026-09-18). 캔버스는 실제 크기로 그리고 무대 폭에 맞춰 축소해 보여준다. 가이드의 소비 프로파일(web 1200/12열 등)과는 별개 값.

## 빌더 왼쪽 칸 규칙 — 2026-09-18

- **탭 두 개**: 「컴포넌트」 · 「패턴」. 탭마다 자기 검색창을 가진다(river 결정 2026-09-18).
- **접힘/펼침**: 처음엔 최상위 갈래만 보인다. 컴포넌트는 registry 분류(Actions·Selection·Form·Table·Navigation), 패턴은 catalog 의 `group`(없으면 "기타") + 「레이아웃 보조」. 펼쳐야 카드가 보이고, 그때 미리보기 그림을 그린다(닫힌 칸은 폭이 0이라 축소 계산이 안 된다).
- **검색**: 찾는 말이 있으면 해당 갈래를 자동으로 펼치고 그 안의 그림도 그린다. 대상 = 정본 영문 이름·id·분류 + registry 의 한글 사용맥락 + 빌더 화면용 한글 찾기말.
  ⚠️ **부품·분류의 한글 이름은 정본에 없다**(`legacy:resolve` 도 "모름"). 카드와 갈래에 붙은 한글은 **빌더 화면용 표시어이지 정본 이름이 아니다**. 정본 승격은 river 결정 사항.
- **플랫폼별 거르기**: 지금 고른 플랫폼의 배포본이 없는 부품은 목록에서 아예 뺀다. 판단은 배포본 manifest 의 `breaks` 키(pc|mobile). `breaks` 가 없는 부품 중 플랫폼이 이름·가이드로 명확한 것만 `PLATFORM_ONLY` 에 적는다(GNB=pc · Mobile Header·Mobile Bottom Nav=mobile). 나머지는 양쪽 공통으로 본다.
- **카드**: 배포 예제 마크업을 그대로 작게 그린 미리보기 + 변형·크기 칩. 칩을 고르고 끌어다 놓으면 그 값으로 들어간다.
- **드래그 앤 드롭**: 카드 → 줄 / 줄 사이. 캔버스 안 요소도 끌어 옮긴다. 끄는 동안에만 "여기에 새 줄" 자리가 열린다.
- **놓는 방식·행 추가는 미리보기 도구줄에** 둔다(river 결정 2026-09-18 — 왼쪽 칸에서 옮김).
- **플랫폼에 없는 부품이 화면에 남아 있으면** 캔버스에서 주황 점선으로 표시하고 속성에 안내를 띄운다(자동으로 지우지 않는다).

## 변형마다 뼈대가 다른 부품 · 화면 끝까지 붙는 부품 — 2026-09-18

river 지적: "헤더가 제대로 생성 안 되어 있고 일부만 만들어져 있다 / 전체 화면에 패딩이 이미 잡혀 있어서 헤더 모습대로 안 들어간다."

- **원인(확인됨)**: 배포본은 부품마다 **예제 마크업 한 벌**만 싣는다. 대부분은 `data-variant` 만 바꾸면 CSS 가 모습을 바꾸지만,
  배포본 manifest 의 `htmlContract.perVariantParts` 가 선언된 **mobile-header(6변형) · gnb(2변형)** 은 변형마다 들어가는 part 자체가 다르다.
  attribute 만 바꾸면 틀린 뼈대가 나온다. (검사 스크립트로 전 부품 확인 — perVariantParts 선언은 이 둘뿐)
- **처리**: 빌더가 `perVariantParts` + `relations` 선언대로 변형별 뼈대를 만든다(`VARIANT_MARKUP`).
  mobile-header 는 가이드 사이트의 같은 생성기(`assets/js/ui-library-guide.js` mobileHeaderMarkup)와 같은 구조를 따른다 — **새 구조를 지어내지 않는다.**
  ⚠️ 가이드 생성기에는 `home-title-1icon` 이 있으나 **배포본 manifest 의 변형 목록(6종)에는 없다.** 빌더는 배포본 목록을 따른다.
- **화면 끝까지(bleed)**: 상·하단 크롬(mobile-header · mobile-bottom-nav · gnb)은 놓을 때 자동으로 「화면 끝까지」가 된다.
  그 줄은 화면 안쪽 여백만큼 좌우로 빼서 그린다(`margin: 0 calc(padding * -1)`). 속성의 「가장자리」에서 끌 수 있다.

## 모바일 기기 크롬(상태바·주소창·툴바·내비) — 2026-09-18 (river 지시)

> "모바일에서는 기본적으로 정본으로 만든 스테이터스 바가 상단에 고정되어 나오면 좋겠어"
> "모바일에서도 웹/앱 선택에 따라 웹바, 내비바가 자동으로 표출되도록 하고싶어"

- **크롬은 배포 부품이 아니다.** 정본(build-components.ts `buildStatusBar` · `buildNavBar`)에는 있지만 **river 결정 D5** 로 웹 배포본에서 뺐다
  ("상태바는 OS·브라우저가 그리는 영역이라 배포본에 넣지 않습니다" — ui-library-guide.js:124).
  `registry/governance/dummy-chrome-parts.json` 도 StatusBar·NavBar·WebTabBar 를 "우리 부품이 아닌 OS 껍데기 소품"으로 선언한다(2026-09-10 river 결정).
- 그래서 **부품 목록에 넣지 않고 미리보기 틀에만** 얹는다. 모바일 틀에서만 보이고 도구줄의 「기기 크롬」에서 앱 · 웹 · 없음 을 고른다(기본 앱).

| 유형 | 위 | 아래 | 정본 대응 |
|---|---|---|---|
| 앱 | 상태바 27 | 안드로이드 내비 45 | StatusBar `Platform=App` · NavBar `Platform=App` |
| 웹 | 상태바 27 + 주소창 50 = **77** | 브라우저 툴바 50 + 안드로이드 내비 45 = **95** | StatusBar `Platform=Web`(360×77) · NavBar `Platform=Web`(360×95) |

- 세부 수치·글리프도 정본 그대로: 상태바(좌 20 / 우 16 · 12 Medium · 묶음 간격 6 · icon/gray-dark) ·
  주소창(h50 · 좌우 16 / 위아래 12 · 간격 6 · 자물쇠 24 + URL 알약 radius full · bg/level-2 · 14 Regular · text/body/tertiary + 새로고침 24) ·
  브라우저 툴바(h50 · 좌우 16 · 뒤로·앞으로·홈·북마크·탭29·메뉴) · 안드로이드 내비(h45 · 좌우 48 · 최근·홈·뒤로). 아이콘 색 icon/gray.
- 앱 유형에서 맨 윗줄이 Mobile Header 면 상태바와 헤더 사이 **16** — 정본 Mobile Header 합성물의 itemSpacing(build-components.ts:3487).
  27 + 16 + 56 = **99**, 정본 주석 "360×99"(:3451)와 같다. 웹 유형은 주소창이 그 자리를 채우므로 넣지 않는다.
- ⚠️ **내보낸 HTML 에는 크롬이 들어가지 않는다.** 실제 기기·브라우저가 그리는 영역이기 때문(D5). 미리보기 전용이다.

## 내용이 화면보다 길 때 — 보기 방식 2가지 (river 결정 2026-09-18)

전에는 처리가 없어서 틀이 그냥 늘어나고 하단 내비가 따라 내려갔다(360×780 인데 높이 1384 가 되고 내비가 1339 에 있던 실측).
도구줄 「보기」에서 고른다. **기본은 기기처럼.**

| 보기 | 동작 | 쓰임 |
|---|---|---|
| **기기처럼**(기본) | 틀을 기기 크기로 고정(모바일 360×780 · PC 1920×1080). 넘치는 내용은 **본문 칸만 스크롤**되고 상태바·하단 내비는 위아래에 붙어 있다. 이름표에 「스크롤 있음」이 붙는다 | 실제로 어떻게 보일지 · 첫 화면에 무엇이 들어가는지 |
| **한눈에** | 내용 길이만큼 틀을 늘려 전체를 본다. 기기 높이 자리에 **「여기까지가 첫 화면」** 점선을 긋는다 | 긴 화면 전체 검수 |

- 구조: `.pb-canvas` > `.pb-shell-top` · **`.pb-scroll`**(본문) · `.pb-shell-bottom`. 기기처럼일 때만 `.pb-scroll` 이 스크롤한다.
- 내보낸 HTML 에는 이 보기 장치가 들어가지 않는다(브라우저가 알아서 스크롤한다). 화면은 `min-height` 로 기기 높이만 지킨다.

## 레거시 화면 내려받기

```
npm run pattern:fetch -- <fileKey> --list                      페이지 목록
npm run pattern:fetch -- <fileKey> <service> --pages <노드들>   그 페이지들 판독
```

Figma 파일을 **열어두지 않아도** 읽는다. 묶음 상자(SECTION) 안까지 들어간다. 조회 한도도 없다.
필요한 건 `.env` 의 파일 읽기 열쇠 하나뿐이고, 그 파일은 저장소에 올라가지 않는다.

> 2026-09-18 이 길이 생기기 전에는 데스크톱 연결로 읽었는데, **열어둔 페이지만 그것도 일부만** 들어왔다.
> 모두앱을 다시 읽으니 화면이 547 → 1084 로 늘었다. 앞으로는 이 길만 쓴다.

## 🖥️ 로컬 모델 쓰는 자리

이 맥 안에서 도는 모델을 쓴다. 클라우드 토큰이 들지 않고, 파일이 밖으로 나가지 않는다.
**판정에는 쓰지 않는다** — 후보를 좁혀주는 데까지다. 규칙을 정하는 것은 사람과 Claude 의 몫이다.

| 쓰는 곳 | 모델 | 지금 상태 |
|---|---|---|
| 닮은 화면 묶기 · 비슷한 화면 찾기 | `qwen3-embedding:0.6b` | ✅ `npm run pattern:similar` |
| 긴 문서에서 어느 대목인지 찾기 | `qwen3-embedding:0.6b` | ✅ 이미 있음 (`npm run docs:find`) |
| 화면 그림을 보고 무슨 유형인지 훑기 | `qwen2.5vl:7b` | 준비됨 — 열쇠로 화면 PNG 를 내려받아 먹인다. 한 장 40초 |
| 문구 다듬기 초안 | — | 쓰지 않는다. 문구는 사람이 정한다 |

### 닮은 화면 묶기

```
npm run pattern:similar -- <service> --cluster
npm run pattern:similar -- <service> --similar "검색 결과가 하나도 없을 때"
```

화면 이름과 쓰인 부품만 벡터로 바꿔 닮은 것끼리 묶는다. 결과는 `inventory/<service>/similar-clusters.md`.
모두앱 1084장 → 묶음 210개, 32초, 클라우드 토큰 0.

준비물은 `ollama serve` 하나다. 안 떠 있으면 스크립트가 그렇게 알려준다.

## 가져온 화면 — 기존 화면 위에 이어 만들기 (river 요청 2026-09-18)

이미 만들어 둔 Figma 화면을 빌더 캔버스에 그대로 올리고, 그 위에 정본 부품을 끼워 넣는다.
가져오는 규칙은 **묶음마다 다르다** — `profile.json` 의 `import.mode`. 모두앱은 `legacy-as-is`(레거시 모습 그대로).

