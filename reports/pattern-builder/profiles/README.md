# 패턴 묶음 (profiles) — 매체·서비스마다 따로 익힌다

> river 결정 2026-09-18: 서비스와 매체에 따라 상황이 너무 달라 하나의 공통 규칙으로 잡기 어렵다.
> 그래서 **매체·서비스마다 특징을 따로 익히고, 그 서비스 화면을 만들 때 그 묶음을 꺼내 쓴다.**

## 묶음 하나 = 매체 + 서비스

```
profiles/<묶음 id>/
  profile.json        어느 매체 · 어느 서비스 · 레거시인가 새것인가
  screen-types.md     화면이 어떤 갈래로 갈리나
  screen-skeleton.md  화면의 세로 칸 나눔 · 폭 · 여백
  composition.md      어떤 부품을 어디에 쓰나
  states.md           화면이 가질 수 있는 상태
  content.md          문구 · 오류 · 접근성
  naming.md           패턴과 화면 이름
```

묶음 id 는 `<매체>-<서비스>` 로 짓는다. 예) `app-modu` · `mweb-signup` · `pcweb-console`.

매체는 넷 중 하나다: `app`(휴대폰 앱) · `mweb`(모바일 웹) · `pcweb`(PC 웹) · `console`(관제·업무용 화면).

## 공통은 미리 만들지 않는다

공통 규칙 자리를 먼저 파 놓고 채우지 않는다. **서로 다른 묶음 셋에서 같은 규칙이 반복될 때** 그때 공통으로 올린다.
억지로 하나로 합치다 실제 화면과 어긋나는 것을 막기 위해서다.

공통으로 이미 있는 것은 **부품과 토큰**뿐이고, 그건 정본에 있으니 여기서 다루지 않는다.

## 닮은 화면 먼저 훑기 (🖥️ 로컬)

새 묶음을 열고 판독을 마쳤으면, 갈래를 손으로 나누기 전에 로컬 모델로 한 번 묶어 본다.

```
npm run pattern:similar -- <service> --cluster
```

결과는 **후보**다. 그 묶음이 곧 패턴이라는 뜻이 아니다. 자세한 것은 [../README.md](../README.md) 의 로컬 모델 자리.

## 화면을 만들 때

1. 어느 묶음으로 만들지 먼저 고른다(매체 + 서비스).
2. 그 묶음의 다섯 갈래만 적용한다. 다른 묶음의 규칙을 끌어오지 않는다.
3. 묶음이 없으면 `_template/` 을 복사해 새로 연다.

## 레거시 묶음

`profile.json` 의 `kind` 가 `legacy` 인 묶음은 **이미 운영 중인 서비스**다.

- 그 묶음의 값은 정본에 합치지 않는다. 정본 신설 근거로 인용하지 않는다.
- 정본이 바뀌어도 그 묶음을 따라 고치지 않는다.
- 최신 부품을 억지로 끼워 넣지 않는다.

## 새 파일이 오면

river 가 주는 Figma 파일은 **서비스별 주요 프로젝트**다. 서비스마다 특이점이 달라 묶음을 따로 만든다.

1. 파일 주소를 받는다 → `npm run pattern:fetch -- <fileKey> --list` 로 페이지 확인
2. 읽을 페이지를 골라 판독 → `inventory/<service>/`
3. `_template/` 을 복사해 묶음을 연다 → `profiles/<매체>-<서비스>/`
4. 로컬 모델로 닮은 화면 묶음 후보를 본 뒤, 다섯 갈래를 근거 있는 것만 채운다

## 지금 있는 묶음

| 묶음 | 매체 | 서비스 | 갈래 | 판독 화면 |
|---|---|---|---|---|
| `app-modu` | 앱 | 모두앱 | legacy | 1084 |
| `pcweb-bus` | PC 웹 | 삼성통근버스 (탑승자) | legacy | 800 |
| `app-bus` | 앱 | 삼성통근버스 (탑승자) | legacy | 633 |
| `pcweb-busadmin` | PC 웹 | 삼성통근버스 (관리자) | legacy | 112 |

> 같은 서비스라도 **매체가 다르면 묶음이 다르다.** 통근버스는 한 페이지 안에 웹 화면과 앱 화면이
> 나란히 그려져 있어 폭으로 갈라 나눴다. 관리자 화면은 쓰는 사람도 화면이 하는 일도 달라 따로 뒀다.
