## ❌ (a)-1 — 배경 스크롤 잠금이 모달과 어긋난다 · manifest 의 설명이 사실과 다르다

**재현(실제 dist 모듈, 픽스처 페이지, 재현율 100%):**

| 단계 | 배경 스크롤 | 기대 | |
|---|---|---|---|
| 0 아무것도 안 열림 | 풀림 | 풀림 | ✅ |
| 1 시트 열기 | 잠김 | 잠김 | ✅ |
| 2 시트 위에 모달 열기 | 잠김 | 잠김 | ✅ |
| 3 **시트만 닫기 (모달은 계속 열려 있음)** | **풀림** | 잠김 | ❌ |
| 4 **모달 닫기 (이제 아무것도 안 열림)** | **잠김인 채 남음** | 풀림 | ❌ |

4단계가 특히 나쁘다 — 아무 오버레이도 없는데 **페이지가 영구히 스크롤 불가 상태로 남는다.** 사용자는 새로고침 말고는 빠져나갈 방법이 없다.

**원인:** `bottom-sheet.js` 와 `modal.js` 가 각자 자기 모듈 안에 별도의 `scrollLock = { count, previous }` 를 갖는다. 서로의 카운터를 못 본다. 나중에 잠근 쪽이 `previous` 에 "이미 잠긴 값(hidden)" 을 저장해 버리는 것이 4단계의 원인이다.

**계약 위반 — 이건 단순 버그가 아니라 문서가 사실과 다른 것이다.**
`ui-library/dist/components/bottom-sheet.manifest.json` 의 `javascript.scrollLockNote`:

> "배경 스크롤 잠금은 열린 시트**(+모달)** 수를 세어 마지막 하나가 닫힐 때만 원래 값으로 되돌린다."

모달까지 함께 센다고 **명시**하고 있으나 코드는 세지 않는다. `modal.manifest.json`·`modal-content.manifest.json` 은 "열린 **모달** 수" 라고만 적어 자기 모듈로 범위를 한정했는데, 이번 manifest 만 범위를 모달까지 넓혀 적었다. 잘못된 주장은 이 작업이 새로 넣은 것이다.

**참고(면죄부 아님):** `modal.js` ↔ `modal-content.js` 사이에도 같은 구조적 결함이 이미 있다. 그러나 ①이번 컴포넌트가 세 번째 독립 카운터를 새로 추가했고 ②거짓 주장을 새로 적었으므로 이 작업의 ❌ 다. 고치는 방법(공용 잠금 모듈로 뺄지, 문구만 정정할지)은 구현자 소관이며 검증자가 정하지 않는다.

## ❌ (a)-2 — `check` 아이콘이 정본보다 굵게 그려진다 (D-8 의 전제가 틀렸다)

⭐ 가 "기계 증명이 없으니 눈으로 봐 달라"고 남긴 자리다. **측정했고, 눈으로도 확인했다.**

24px 프레임 기준 실측(캔버스 ×20 초과표본, alpha>0.12):

| | 웹 자산(16 프레임 → 24 확대) | 정본 원본 내보내기(`ic_확인_line.png` 48px = 24 기준) | 차이 |
|---|---|---|---|
| 잉크 가로 | **16.80** | **18.40** | −1.60px |
| 잉크 세로 | 12.10 | 12.30 | −0.20px |
| 잉크 면적 | **48.87** | **38.85** | **+26%** |
| 환산 선 굵기 | **약 2.27px** | 약 1.5~1.8px | **약 +50%** |
| 중심 좌표 | (12.00, 12.15) | (12.00, 12.05) | 일치 |

**핵심은 D-8 이 보지 않은 축이다.** 16 프레임 자산을 24 로 비례 확대하면 잉크 비율만 커지는 게 아니라 **선 굵기도 같이 1.5배가 된다**(1.5 → 2.25). D-8 은 잉크 *비율*(72.5% vs 75%)만 견주어 "차이 0.6px" 이라고 결론했는데, 실제 가로 차이는 1.6px 이고 진짜 문제는 굵기다. 이것이 「시각 매칭 2대 원리」②(프레임 크기 ≠ 내용물 크기)가 잡으라고 있는 종류의 실패다.

**눈으로도 분명하다.** 같은 24px 로 그린 다섯 아이콘을 나란히 확대해 보면 `check` 하나만 확연히 굵다 — `chevron`·`lock`·`close`·`account` 는 전부 24 프레임 원본이라 선이 가늘고 서로 일관된다. 이 다섯 중 `check`·`chevron`·`lock` 은 **Bottom Sheet Option 한 목록 안에서 같은 24px 로 나란히 선다**(Text:Selected 의 체크 ↔ List:Default 의 화살표 ↔ List:Disabled 의 자물쇠). 한 목록 안에서 한 아이콘만 무게가 다르면 바로 보인다.

이건 정본 ↔ 파생 불일치다. **두 갈래 분류를 적용하지 않는다**(하드룰 H6① — 정본↔파생에는 금지). 파생을 정본 쪽으로 맞춘다.

`check.svg` 자체를 건드리면 16px 로 쓰는 `checkbox` 가 깨진다 — 해법(24 프레임 자산 추가 등)은 구현자가 정한다.

## ❓ (c)-1 — 새 독립 Bottom Sheet 의 "딤 눌러 닫기" 는 river 확인이 필요하다

⭐ 의 사실 주장은 **맞다.** 직접 확인했다 — 이관 전 `date-picker.js`(git HEAD 560줄)가 이미 `sheetBackdrop` 클릭으로 닫고 있었다. 그러니 **date-picker·time-picker 에서 이 동작을 유지한 것은 퇴행 방지가 맞고, 여기엔 이견이 없다.**

갈라지는 지점은 **새로 만든 독립 `bottom-sheet`** 다. 이 컴포넌트에는 지킬 기존 동작이 없다. manifest 스스로 `notInCanon.backdropClickToClose` 에 "정본에 없다" 고 적었다 — 즉 정본에서 유도되지 않는 UX 결정이다.

- river 는 **모달**에 대해 "딤 클릭으로 닫지 않는다" 를 직접 결정했다(2026-09-02 범위 A). 딤 동작이 river 가 의견을 가진 주제라는 뜻이다.
- ⭐ 는 배포된 시트 1종의 동작을 **"시트류 전체의 규칙"** 으로 일반화했다. 근거 없는 자리를 스스로 규칙으로 메우는 모양이라 하드룰 H6② 가 경계하는 형태에 가깝다.
- 다만 완전한 위반이라고 단정하기도 어렵다 — 실제로 승인된 선례가 존재하기 때문이다.

그래서 임의 판정하지 않고 **(c) 로 올린다.** 물을 것은 딱 하나다:

> **새로 만든 독립 바텀시트도 어두운 배경을 누르면 닫힐까요?**
> (A) 닫힌다 — 지금 만든 대로. 달력·시간 시트와 동작이 같아진다.
> (B) 닫지 않는다 — 모달과 같은 규칙. 달력·시간 시트는 지금처럼 닫히는 채로 둔다(이미 배포돼 있어 바꾸면 퇴행).
> 안 정하면 (A) 로 나갑니다.

범위를 좁혀 둔다: date-picker·time-picker 의 딤 닫기는 **질문 대상이 아니다**(유지가 맞다).

### 손잡이 2개 — 편법 아님, 정당한 조절 지점이다 (판정)

판정 근거 네 가지:

1. **정본이 실제로 다르다.** 위에서 직접 읽어 확인했다(48/raised-up ↔ 32/none). 값 하나를 고르면 반드시 어느 한쪽이 틀린다.
2. **코어 내부를 덮어쓰지 않는다.** 소비자 CSS 는 `[data-s1-component="bottom-sheet"]` **루트**에 사용자 지정 속성만 준다. 계약이 금지한 것은 "다른 코어의 **내부 part** 를 선택하거나 시각 스타일을 override" 인데, 루트는 내부 part 가 아니고 넘기는 것도 시각 속성이 아니다.
3. **선례가 있다.** `mobile-bottom-nav` 가 `--s1-mobile-nav-icon` 을 같은 방식으로 공개하고 있으며 이미 승인·배포됐다. 새로 만든 우회로가 아니다.
4. **대안이 전부 더 나쁘다.** 변형축 신설 = 정본에 없는 축 발명(금지) · 소비자가 `sheet-panel` 선택자 덮어쓰기 = 계약 위반 · CSS 두 벌 유지 = 이번 작업이 없애려던 것.

덧붙여 계약의 `compositionOwner` 는 "자식 사이의 gap·배치" 를 부모/패턴 소유로 규정한다 — 부모(picker)가 시트 안 간격을 주는 것은 오히려 그 규정대로다. manifest `cssContract.customProperties` 에 공개 계약으로 문서화돼 있어 뒷문이 아니다. **(c) 로 올리지 않는다.**

### 토큰·색

두 CSS 파일에 **하드코딩 hex·rgb 0건.** 참조한 사용자 지정 속성 32개를 `tokens.css`·`typography.css` 에서 전수 확인 — **미정의 0건.** 남은 raw px 는 전부 정본 숫자 리터럴(360·48·40·24) 이며 정본에 Variable 바인딩이 없는 값들이다. Light·Dark 는 별도 사본 없이 같은 Semantic 토큰의 mode 로만 갈린다.

## 상태 플래그에 대한 판정 (⭐ §7)

⭐ 가 `draft` → `verified` 를 직접 올린 것은 **형식상 자기승인이 맞다.** 그 플래그는 이름이 "verified" 이고, `ui:guide:render` 검사기가 도는 대상까지 결정한다 — 즉 플래그를 올린 행위가 그 검사기의 초록을 만들어 냈고, 그 초록이 4-verification §1 에 기계검사로 실렸다.

다만 **정상 참작이 크다.** ①안내 화면을 열 다른 스위치가 없었고 ②⭐ 가 §1·§7 에 그 사실과 한계를 먼저, 정확히 적었고 ③"독립 검증이 ❌ 를 내면 draft 로 되돌린다" 고 미리 약속했다. 숨긴 것이 없으므로 별도 ❌ 로 세지 않는다.

**지금 FAIL 이므로 그 약속이 발동한다 — 두 manifest 의 `status` 를 `draft` 로 되돌려야 한다.** 되돌리면 `ui:guide:render` 는 다시 두 컴포넌트를 건너뛰므로, 재검증 때 그 초록을 근거로 쓰지 않도록 주의한다.

구조적 제안(검증자 권고, 강제 아님): 화면 노출용 스위치와 검증 결과 플래그가 같은 필드를 쓰는 한 이 자기승인은 매번 반복된다. 분리가 필요하면 별건으로 올리는 것이 맞다.
