# 사양 변경 — 프레임 네이밍 체계 적용 (2026-08-25)

## 왜

Figma 화면 프레임 이름이 레거시 기획서 목차 번호(`2.1 로그인_1 최초진입`)를 그대로 쓰고 있었다. 문제:

- `2.1` 은 없어진 기획서의 장 번호다. 패턴 체계 안에서 의미가 없다.
- 삭제된 상태(3·4번) 때문에 번호에 구멍이 났고, 남은 번호가 캔버스 순서와도 흐름 순서와도 맞지 않았다.
- `자동 로그인 선택 B` 는 실제로 **선택이 아니라 설정 완료 안내**였다 — 이름이 내용과 달랐다.
- `새로운 기기로 로그인 A~E` 5개 중 A·B·C 만 팝업이고 D·E 는 팝업 없는 기본 로그인 화면이었다. 한 묶음처럼 보이지만 성격이 달랐다.
- 결과적으로 **이름만 보고는 사람도 AI 도 그 화면이 어느 플랫폼·어느 패턴·흐름의 어디인지 알 수 없었다.**

### 3. 중복 화면 삭제 — `1562:15`

`1-inventory.md` 의 레거시 재고조사 기록:

> `8403:60218`, `21446:2852` 는 같은 신규기기 묶음에 놓인 **팝업 전·후 기본 로그인 상태**다.

즉 `1562:14`(팝업 전 = 로그인 실행 직전)와 `1562:15`(팝업 후 = 인증 완료 뒤 다시 로그인) 는 **흐름 위치가 다른 상태**였다. 다만 두 화면의 표현은 완전히 동일하고, 차이는 보조 버튼 문구(`휴대전화번호로 로그인` vs `휴대폰 번호로 로그인`)뿐이었다 — 이는 상태 차이가 아니라 레거시 문구 불일치다.

별도 프레임을 유지할 근거가 없어 `1562:15` 를 삭제하고, 분기 복귀(`4c2` → `4`)는 프로토타입 연결로 표현하기로 했다. **river 승인** (제거 근거를 다시 확인한 뒤 재확인).

## 무엇을 안 바꿨나 (기계 증명)

화면 내부 구조·컴포넌트·토큰·문구는 **일절 건드리지 않았다.**

```
npm run snapdiff -- snapshot-before.json snapshot-after.json --expect snapshot-expect.json
→ 추가 0 · 삭제 1 · 변경 32 · violations=0 (종료코드 0)
```

스냅샷은 섹션·화면 프레임의 전 속성에 더해 **화면 내부를 전수 순회한 구조 다이제스트(`hx`)와 노드 수(`c`)** 를 담는다. diff 결과에 `hx`·`c` 변경이 한 건도 없다 = 화면 내부 노드 **1,132개 전부 무변경**. 변경 32건의 내역은 이름 10 · 자식순서 7 · x 7 · y 6 · Section 폭 1 · Section 높이 1 로, `snapshot-expect.json` 의 사전 선언과 개수까지 일치한다.

아래는 **당시 증거로 보존**하며 현재 기준선으로 인용하지 않는다.

# 라운드3 — 집행 장치 배선 (2026-08-25)

## Gate 42 — 화면 네이밍 (신규, 차단)

`scripts/screen-naming-check.js` · `npm run screens:naming`

`registry/patterns/{id}/states.md` 의 '프레임 이름' 열을 정책 정본과 대조한다. 검사 항목: 서식 정규식 · 흐름 코드 문법 · **분기가 실재하는 기본 흐름 단계에서 갈라지는지** · 이름/흐름코드 중복 · 선언된 화면 수. 대상은 정책 `adopted[]` 등재 패턴만(래칫).

**자가 시험(위반 주입 → 원복)으로 실제 차단을 확인했다:**

| 주입한 위반 | 잡혔나 |
|---|---|
| 레거시 서식 `2.1 로그인_2 입력 A` | ✅ |
| 부모 없는 분기 `9z1`(기본 흐름 `9` 부재) | ✅ |
| 흐름 코드 중복(`4c1` 두 개) | ✅ (**첫 구현은 못 잡았다** — 전체 이름으로만 비교해 상태명이 다르면 통과. 코드 기준 비교로 고침) |
| 위반 있는 상태에서 `npm run gate:check` | ✅ **exit 1 차단** · 원복 후 exit 0 |

> **한계(정직 표기):** 지키는 것은 **기준표의 이름**이지 Figma 실물 프레임 이름이 아니다. 커밋 훅은 저장소만 읽으므로 실물 스캔에 필요한 MCP 를 못 쓴다. 실물↔문서 일치는 화면 작업 시 `component-verifier` 소관이고, `screen-rebuilder` 는 이 표의 이름을 그대로 쓰도록 배선했다(라운드1).

## Gate 41 — 화면 작업 상태 (기존 검사기를 자동 실행에 배선, warn)

`screen-rebuild:statecheck` 는 **존재했지만 수동**이라 2026-08-21~24 사이 실패를 아무도 몰랐다. `--all` 모드(자기 자신을 플로우마다 자식 프로세스로 실행)를 붙여 Gate 41 로 배선했다.

**배선하자마자 아무도 모르던 기존 불일치 1건이 드러났다:**

```
✅ login/pc-web
✅ modu-app/login-mobile (경고 2)
❌ modu-app/signup-mobile-web — screens[2]에 sourceNodeId와 name이 필요합니다.
```

진행 중인 회원가입 플로우의 데이터 문제이며 이 작업 범위 밖이라 손대지 않았다. Gate 41 은 **warn 단계**라 커밋을 막지 않는다(래칫 — 기존 부채 정리 후 승격 검토).

### 낡음(`_stale`) 규약 존중 — HD-2 의 A안

`screen-spec.json`·`scan-summary.json` 은 13화면 시절 증거라 화면 수를 현재와 비교하면 영원히 실패한다. 이 프로젝트는 이미 "`_stale: true` 인 파일은 판정 근거로 인용하지 않는다"를 규약으로 선언해 뒀는데 **검사기가 그 규약을 안 지키고 있었다.**

고친 방식은 "건너뛰기"가 아니다:

- `_stale: true` **이면서 `_supersededBy`(대체 문서)가 있을 때만** 오류를 경고로 낮춘다
- 제외한 파일 이름·대체처·표시 날짜를 출력한다(감사 흔적)
- 도장만 있고 대체처가 없으면 **인정하지 않고 그대로 오류**

즉 검사가 사라지는 게 아니라 감사 흔적을 남기고 경고로 내려간다. 결과: 이 플로우 오류 2건 → **0건 + 경고 2건**.
