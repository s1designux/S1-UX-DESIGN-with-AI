# 의도 선언서 — 모바일 웹 회원가입 (2026-08-24)

> **이 문서의 성격:** 레거시 원본에 **존재하지 않는 부분**의 기준이다. river 가 선언했고, 그 선언이 곧 정답지다.
> 레거시가 있는 9개 화면은 이 문서가 아니라 `1-inventory.md`(원본 전수표)가 기준이다.
> 승인: river · 2026-08-24

---

## 왜 이 문서가 필요한가

레거시(`aLxh458o9BRXklRFM3YYzk` / `32443:31901`)의 회원가입 흐름은 **약관 동의 → 약관 상세 → 아이디 입력**으로 바로 이어진다. **본인인증 단계가 없다.**

현재 의도하는 흐름에는 본인인증이 들어가므로, 그 부분은 베낄 원본이 없다. 원본이 없을 때 에이전트가 빈자리를 임의로 메우는 것은 금지되어 있으므로(하드룰 H6②), 사람이 선언한 이 문서가 그 자리를 대신한다.

---

## 1. 본인인증 단계

### 진입

**약관 동의 화면(`_1`)의 [본인인증] 버튼**을 누르면 진행한다.

### 외부 사이트는 재현하지 않는다

본인인증은 **외부 본인인증 사이트**로 넘어가서 이루어진다. 그 사이트 화면은 **우리 디자인시스템이 아니므로 재현하지 않는다.**

- 우리가 통제할 수 없다 — 그쪽이 바꾸면 우리 패턴이 틀려진다.
- 소비자(퍼블리셔·개발)가 알아야 할 것은 그 사이트의 생김새가 아니라 **"여기서 나갔다가 언제 어떤 상태로 돌아오는가"** 이다.

대신 **플레이스홀더 1장**을 두어 **"인증 단계가 중간에 있다"는 사실만 인지**되게 한다. 기기 크롬·OS 키보드와 같은 취급이다(정본 컴포넌트로 그리지 않는다).

### 결과별 이동

| 결과 | 이동 | 우리 화면 |
|---|---|---|
| **성공** | 아래 §2 의 두 갈래로 분기 | 있음 |
| **취소** (사용자가 중단) | **약관 동의 화면(`_1`)으로 복귀** | 있음 (복귀만) |
| **실패** | **외부 사이트가 자체적으로 재시도를 처리**한다 | **없음** — 우리 화면을 만들지 않는다 |

> 실패 화면을 만들지 않는 것은 누락이 아니라 **의도된 범위 밖**이다. 인증 실패의 처리 주체가 외부 사이트이기 때문이다.

## 2. 인증 후 두 갈래

인증이 확인되면 사용자 상태에 따라 갈린다.

### (a) 진짜 신규 가입

다른 에스원 서비스를 쓴 적이 없는 사용자다.

→ **아이디 입력 화면(`_3`)** 으로 이동해 직접 입력한다.

### (b) 기존 아이디 보유

이미 다른 서비스(**홈페이지 또는 웹뷰어**)를 사용 중이라 계정이 있는 사용자다.

→ **기존 아이디 선택(`_4`, 바텀시트)** 이 제공된다.

- 목록에서 **기존 아이디를 선택**하면 그대로 사용한다.
- **기존 아이디를 원하지 않으면 새 아이디를 쓸 수 있다** — 시트를 닫고 직접 입력한다.

> 레거시의 `_4` 화면은 아이디 입력 화면 위에 바텀시트가 올라온 형태다. 이 구조는 위 의도와 맞는다(시트를 닫으면 그 아래가 직접 입력 화면).

## 3-1. 웹 ↔ 앱 관계 (2026-08-24 river 추가 선언)

**앱은 웹 화면을 끌어다 쓰는 하이브리드다.** 따라서 **웹과 앱 화면은 완전히 동일해야 한다.**

| 항목 | 처리 |
|---|---|
| 화면 구성·문구 | **완전 동일** — 갈리면 안 된다 |
| 상하단 크롬 | 웹=StatusBar `Platform=Web`(주소창) / 앱=`Platform=App` — **variant 교체만** |
| **마지막 완료 화면** | **여기만 다르다** — 앱=회원가입 완료 / 웹=앱 설치 안내 |
| 「이미 회원으로 가입되어 있다」 팝업 | 앱에만 있고 **웹에 누락된 상황** — 웹에도 있어야 한다 |

### 지금 갈려 있는 문구는 정책 차이가 아니다

레거시에서 웹과 앱의 문구가 일부 다르지만(비밀번호 `8자 이상` vs `8~15자`, 이메일 헬퍼), 이는 **의도된 차이가 아니라 레거시 관리 부실**이다. 원본대로 각자 유지하지 않는다.

**river 가 웹 문구를 검토해 정본에 반영하고, 반영된 문구를 앱에 그대로 쓴다.** 빌드 기준은 레거시 원문이 아니라 **확정 문구**다. 검토 목록은 `copy-review.md`.

### 작업 순서

**웹을 먼저 정리한다.** 앱은 완성된 웹 화면에서 **NavBar variant 교체 + 완료 화면만 교체**해 재사용한다.

## 3-2. 선행 조건 — 모바일 헤더 컴포넌트 (2026-08-24)

20개 화면 전부에 앱바가 들어가는데 **모바일 헤더 컴포넌트가 정본에 없다.**

- V2.4 `mobile_header`(`540:6112`)에 5종 존재: `standard_title` · `standard_title + close btn` · `Home title_icon 2` · `Home title_sub title_icon 1` · `Home titel + alt titel` (각 360×99)
- **「타이틀 없는 유형」 1종을 신설**해 총 6종으로 만든다(river).

**이것이 끝나기 전에는 회원가입 화면을 빌드하지 않는다.**

앱바 제목이 렌더에서 안 보이는 것은 **원본대로 맞다**(river 확인). 화면마다 이미 큰 타이틀이 있어 중복되지 않는다.

## 4. 플랫폼

**모바일 웹**이다. 회원가입은 **통합계정 화면을 끌어온 것**이라 브라우저 크롬(상단 `m.s1.co.kr` 주소창)이 원본 그대로다.

로그인 패턴은 앱(App) 기준으로 만들었으므로 **크롬이 다르다.** 두 패턴을 같은 플랫폼으로 억지로 맞추지 않는다. (로그인은 모바일 웹·앱 둘 다 제공되지만, 현재 정리된 로그인 패턴은 앱 기준이다.)
