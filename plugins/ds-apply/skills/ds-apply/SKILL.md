# ds-apply — 디자인시스템 값을 프로토타입에 입히는 스킬

## 이 스킬이 왜 필요한가 (실패에서 역산)

프로토타입·테스트 사이트를 만들 때 사람이 손으로 색을 넣으면 거의 항상 `#2A2A2E` 같은 **하드코딩 값**을 쓰게 된다. 디자인시스템 저장소의 가이드 사이트조차 인라인 HEX 가 섞여 있을 만큼 이건 흔한 실수다. 하드코딩된 화면은 디자인시스템이 바뀌어도 따라오지 못하고, 다크모드도 깨진다.

이 스킬은 그 실수를 구조적으로 막는다. **값을 지어내지 않고, 딸려 있는 값 파일에서만 가져와서** 화면을 만들거나 고친다.

## 핵심 구조 — 값의 원천은 딱 두 파일

값은 `references/` 폴더의 두 파일에서만 가져온다. 이 파일들이 어떻게 들어오는지는 **설치 경로에 따라 다르다.**

- **배포판으로 설치한 경우**(zip 반입 · 플러그인 설치) — 두 파일이 **이미 들어 있다.** 원본 저장소(S1-UX-DESIGN-with-AI)가 없어도 이 두 파일로 완결된다.
- **원본 저장소를 클론한 경우** — 두 파일은 저장소에 커밋되지 않으므로 **처음엔 없다.** (원본이 같은 저장소에 있어, 사본을 커밋하면 드리프트가 생기기 때문) 저장소 루트에서 `node release-skill.js --sync` 를 한 번 실행하면 채워진다.

- **`references/tokens.css`** — 토큰의 **실제 값**. 라이트/다크 색, 간격, 크기, 반경, 타이포. `[data-theme="dark"]` 블록에 다크 값이 있다.
- **`references/DESIGN.core.md`** — 컴포넌트를 **언제·어떻게** 쓰는지, 어떤 variant×state 가 있는지, 각 상태가 **어떤 토큰 이름**을 쓰는지.

> 관계: DESIGN.core.md 가 "이 버튼은 `--button-primary-default-bg` 토큰을 쓴다"고 알려주고, tokens.css 가 "그 토큰의 실제 값은 이 색"이라고 알려준다. 둘은 짝이다. 하나만 보면 반쪽이다.

## 시작 전 필수 점검 (모든 작업 공통)

작업을 시작하기 전에 **값 파일 두 개가 실제로 있는지 먼저 확인한다.**

- `references/tokens.css`
- `references/DESIGN.core.md`

하나라도 없으면 **작업을 시작하지 말고** 아래를 그대로 보고하고 멈춘다.

> 값 파일이 없습니다. 저장소를 클론한 경우라면 저장소 루트에서
> `node release-skill.js --sync` 를 먼저 실행하세요.
> (배포판으로 설치했는데도 없다면 배포가 잘못된 것이니 담당자에게 알리세요.)

⚠️ 이 점검을 건너뛰면, 파일이 통째로 없는 상황을 아래 절대규칙 1번의 "이 값은 토큰에 없음"으로 **잘못 보고**하게 된다. 원인이 전혀 다르므로 반드시 구분한다.

## 절대 규칙 (모든 작업 공통)

1. **값을 지어내지 않는다.** 색·간격·크기·반경·타이포는 `references/tokens.css` 에 있는 것만 쓴다. 없으면 "이 값은 토큰에 없음"이라고 보고하고 멈춘다. 비슷한 값으로 반올림하거나 추측하지 않는다.
2. **HEX 를 직접 쓰지 않는다.** 코드에는 항상 `var(--토큰이름)` 형태로 쓴다. (유일 예외: `--color-overlay` 계열의 rgba 알파)
3. **Foundation 팔레트를 직접 참조하지 않는다.** `var(--color-gray-500)` 처럼 팔레트를 직접 쓰지 말고, 반드시 Semantic·컴포넌트 토큰을 경유한다. (예: `var(--color-text-body-primary)`)
4. **references 안의 값 파일은 읽기 전용이다.** tokens.css, DESIGN.core.md 를 이 작업 중에 고치지 않는다. (그 파일들은 원본 저장소에서만 갱신된다)
5. **다크모드는 `[data-theme="dark"]` 구조를 따른다.** 토큰 이름은 그대로 두고 값만 다크용으로 바뀌므로, `var(--토큰)` 을 제대로 쓰면 다크는 자동으로 따라온다. 다크용 색을 따로 하드코딩하지 않는다.
6. **폐지된 것을 재도입하지 않는다.** Button 의 `danger`·`ghost` variant 는 폐지 확정이다.
7. **상태 7종을 빠뜨리지 않는다.** 인터랙티브 요소는 default·hover·pressed·focus·selected·disabled·error 를 고려한다. (해당 없는 상태는 "해당없음"으로 명시)

## 작업 A — 기존 화면을 디자인시스템으로 교체

사용자가 "이 화면 우리 시스템으로 맞춰줘" 라고 할 때.

### 1단계 — 하드코딩 값 수집
대상 파일에서 아래를 전부 찾아 목록으로 만든다.
- 인라인 HEX (`#RRGGBB`, `#RGB`)
- rgb()/rgba() 직접 값
- 하드코딩된 px (색이 아닌 간격·크기·반경·폰트도)

### 🚦 검문소 1 (STOP)
수집한 하드코딩 값 목록을 사용자에게 먼저 보여준다. "몇 개를 찾았고, 어디에 있는지." 사용자 확인 없이 교체로 넘어가지 않는다.

### 2단계 — 토큰 매칭
각 하드코딩 값을 `references/tokens.css` 의 토큰과 대조한다.
- 정확히 일치하는 토큰이 있으면 → 그 `var(--토큰)` 으로 교체 후보
- 일치하는 게 없으면 → "매칭 실패" 목록에 넣는다. **임의로 가장 가까운 토큰을 고르지 않는다.**
- 매칭 시 규칙 준수: Semantic·컴포넌트 토큰 우선, Foundation 직접 참조 금지

### 🚦 검문소 2 (STOP)
매칭 결과를 표로 보여준다: `원래 값 → 교체할 토큰`. 그리고 **매칭 실패 목록**을 따로 보여준다. 매칭 실패가 있으면 사용자에게 "이 값들은 토큰에 없다. 어떻게 할지" 물어본다. 확인 전에는 파일을 고치지 않는다.

### 3단계 — 교체
승인된 매칭만 `var(--토큰)` 으로 교체한다. 매칭 실패 항목은 건드리지 않고 그대로 둔다(주석으로 표시).

### 4단계 — 완료 보고 (아래 형식)

## 작업 B — 신규 프로토타입을 디자인시스템으로 생성

사용자가 "이 기능 프로토타입 만들어줘" 라고 할 때.

### 1단계 — 필요한 컴포넌트 파악
만들 화면에 어떤 컴포넌트가 필요한지 나열한다 (버튼, 입력, 모달 등).

### 2단계 — DESIGN.core.md 에서 사용법 확인
각 컴포넌트에 대해 `references/DESIGN.core.md` 를 열어 확인한다.
- 언제 쓰나 / 쓰지 말아야 할 때
- 어떤 variant 가 공식인가 (폐지된 것 제외)
- 어떤 state 가 있고, 각 state 가 어떤 토큰 이름을 쓰나

### 🚦 검문소 1 (STOP)
"이런 컴포넌트를, 이런 variant 로 쓰겠다"는 계획을 먼저 보여준다. 사용자 확인 후 코드 작성으로 넘어간다.

### 3단계 — 토큰으로 구성
`references/tokens.css` 의 `var(--토큰)` 만 사용해 화면을 만든다.
- 색·간격·크기·반경·타이포 전부 토큰으로
- 절대 규칙(HEX 금지, Foundation 직접 참조 금지, 다크 구조) 준수
- tokens.css 에 없는 값이 필요하면 → 지어내지 말고 "이 값은 토큰에 없다"고 보고

### 4단계 — 완료 보고 (아래 형식)

## 실행 방법

사용자는 보통 다음처럼 말한다:
- "이 화면 우리 디자인시스템으로 맞춰줘" → 작업 A
- "이거 하드코딩된 색 다 토큰으로 바꿔줘" → 작업 A
- "회원가입 프로토타입 우리 시스템대로 만들어줘" → 작업 B
- "이 기능 화면 짜줘, 다크모드도" → 작업 B

## 완료 보고 (필수)

작업이 끝나면 아래 표로 보고한다. 건너뛴 단계가 있으면 그 이유를 밝힌다.

```
## ds-apply 완료 보고

작업 유형: A(교체) / B(생성)
대상 파일: <경로>

| 항목 | 결과 |
|------|------|
| 처리한 값 개수 | N개 |
| 토큰으로 교체/적용 | N개 |
| 매칭 실패 (토큰에 없음) | N개 |
| HEX 직접 사용 잔존 | N개 (0이어야 정상) |
| 다크모드 대응 | 됨 / 해당없음 |

매칭 실패 목록 (사용자 판단 필요):
- <값> @ <위치> — 이유

값 출처: references/DESIGN.core.md, references/tokens.css
(버전: references/VERSION.txt 참조)
```

## 값 파일이 낡았을 때

이 스킬의 값 파일(references/)은 원본 저장소에서 갱신되어 배포된다. 작업 중 "토큰에 있어야 할 것 같은데 없다" 싶으면, 값 파일이 낡았을 수 있다. **그 자리에서 값을 지어내지 말고**, "값 파일이 최신인지 확인이 필요하다"고 사용자에게 알린다.
