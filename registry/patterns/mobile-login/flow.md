# Mobile Login 흐름과 이유

## 기본 흐름

| 프레임 코드 | 단계 | 사용자·시스템 상태 | 다음 조건 |
|---|---|---|---|
| `1` | 최초 진입 | 아이디와 비밀번호가 비어 있고 로그인 버튼이 비활성 | 사용자가 입력 시작 |
| `2` · `3` | 부분 입력 | 한 입력창이 편집 중이며 키보드가 열림 | 두 입력값이 모두 채워질 때까지 로그인 비활성 |
| `4` | 입력 완료 | 아이디와 비밀번호가 모두 입력되고 로그인 버튼이 활성 | 사용자가 로그인 실행 |
| `4` → 분기 | 서버 판정 | 클라이언트가 자격 증명을 서버에 전달 | 성공·불일치·새로운 기기 중 하나로 분기 |
| `4a` · `4b` · `4c` | 후속 처리 | 필요한 경우 자동 로그인 또는 새로운 기기 안내 | 확인 완료 후 서비스 진입 또는 재로그인 |

**세 분기는 모두 `4`(로그인 실행)에서 갈라진다.** 프레임 이름의 `4a`·`4b`·`4c` 가 그 사실을 담고 있다 — `4c2` 는 "기본 흐름 4번째 화면에서 갈라진 세 번째 분기의 2번째 화면"이라는 뜻이다. 표기 규칙은 `registry/governance/screen-naming-policy.json`.

키보드 열림은 별도의 업무 단계가 아니라 2단계와 3단계의 **표현 상태**다. 화면 높이를 침범하지 않도록 `NavBar / Platform=App + Keyboard` 정본을 사용한다.

## 분기

### `4a` — 자격 증명 불일치

서버가 아이디 또는 비밀번호 불일치를 반환하면 두 입력창을 함께 오류로 표시하고 통합 메시지를 제공한다. 사용자가 값을 수정하면 다시 로그인할 수 있다.

이유:

- 클라이언트가 어느 값이 틀렸는지 단정할 수 없다.
- 특정 계정의 존재 여부를 노출하지 않는다.
- 비밀번호만 오류로 표시해 잘못된 원인을 암시하지 않는다.

### `4b` — 자동 로그인

로그인 성공 후 자동 로그인을 제공하는 서비스는 사용자의 명시적인 동의를 받는다. 설정 결과를 별도 안내해야 하는 서비스는 확인 모달을 이어서 제공할 수 있다.

이유:

- 자동 로그인은 기기 분실·공용 기기 사용 시 보안에 영향을 준다.
- 단순한 기본값이 아니라 사용자가 이해하고 선택한 설정이어야 한다.

### `4c` — 새로운 기기

서버가 현재 기기를 인증되지 않은 기기로 판정하면 서비스 정책에 맞춰 다음 안내 중 필요한 상태를 사용한다.

- 본인 인증 필요 안내
- 인증 완료 후 재로그인 안내
- 현재 기기를 인증 기기로 등록할지 확인

세 상태를 항상 한 줄로 순차 노출하는 것은 아니다. 서버 응답과 서비스의 기기 인증 정책에 맞는 상태를 선택한다.

이유:

- 계정 탈취와 무단 기기 등록을 줄인다.
- 기존 인증 기기의 해제나 교체처럼 사용자에게 영향을 주는 결과를 미리 알린다.
- 인증 완료와 실제 로그인 완료를 구분한다.

`4c2`(기기 인증 완료)에서 "다시 로그인" 안내를 받은 사용자는 `4`(입력 완료)로 돌아간다. 두 상태의 화면 표현이 같으므로 복귀용 프레임을 따로 두지 않고 프로토타입 연결로 표현한다.

## 사용하지 않는 흐름

- 아이디·비밀번호 형식을 입력 중에 검증하는 흐름
- 아이디 미입력·비밀번호 미입력을 제출 후 오류 화면으로 따로 분리하는 흐름
- 서버 판정 전에 계정 존재 여부를 추측하는 흐름
- 로그아웃 확인이나 서비스 메뉴 탐색 흐름

로그아웃은 인증 이후의 별도 패턴으로 다룬다.
