# PC Login 흐름과 이유

## 기본 흐름

| 프레임 코드 | 단계 | 사용자·시스템 상태 | 다음 조건 |
|---|---|---|---|
| `1` | 최초 진입 | 아이디·비밀번호가 비어 있고 로그인 버튼이 비활성 | 사용자가 입력 시작 |
| `2` | 아이디 입력 중 | 아이디 칸 포커스, 비밀번호 빈칸, 로그인 비활성 | 비밀번호까지 채워질 때까지 비활성 |
| `3` | 비밀번호 입력 중 | 아이디 입력됨, 비밀번호 칸 포커스·마스킹, 로그인 활성 | 사용자가 로그인 실행 |
| `4` | 입력 완료 | 두 칸 모두 입력, 포커스 없음, 로그인 활성 | 로그인 실행 → 서버 판정 |
| `4` → 분기 | 서버 판정 | 자격 증명을 서버에 보냄 | 성공 시 서비스 진입, 실패 시 `4a` |

**분기는 모두 `4`(로그인 실행)에서 갈라진다.** 표기 규칙은 `registry/governance/screen-naming-policy.json`.

## 분기 `4a` — 로그인 실패

서버 응답의 종류에 따라 세 상태 중 하나를 쓴다. 세 상태 모두 표현 방식은 같다 — 두 입력칸 오류 테두리, 비밀번호 칸 아래 문구 한 번, 로그인 버튼은 활성 유지.

| 코드 | 언제 | 안내 |
|---|---|---|
| `4a1` | 아이디·비밀번호 불일치 (1~4회) | 통합 오류 + 현재 시도 횟수 `(1/5)` |
| `4a2` | 5회 실패 | 통합 오류 + 잠금 시간 `(최대 5분)` |
| `4a3` | 사용이 중지된 계정 | 관리자 문의 안내 |

이유:

- 클라이언트는 어느 값이 틀렸는지 단정할 수 없고, 계정의 존재 여부를 드러내지 않아야 한다.
- 비밀번호 칸만 오류로 칠하면 원인을 암시하게 된다.
- 잠금·사용 중지를 별도 화면이나 상자로 띄우지 않고 같은 자리에 두면, 사용자는 한 곳만 보면 된다(모바일 로그인과 같은 규칙).
- 잠금 화면을 따로 두지 않는다 — 기준 자료(레거시)도 문구 꼬리만 다르고 별도 화면이 없다.

사용자가 값을 고치면 `4`(입력 완료)와 같은 상태로 돌아가 다시 로그인할 수 있다. 복귀용 프레임은 따로 두지 않는다.

## 사용하지 않는 흐름

- 입력 중 형식 검증, 빈칸 제출 후 오류 화면
- 아이디 저장 체크(2026-10-02 river 결정으로 뺌 — 보조 링크로 대체)
- 언어 목록 펼침, 약관 팝업, 비밀번호 보기/숨기기 전환 — 해당 정본 상태가 없거나(LoginGNB 펼침·Input 보기/숨기기 축 없음) 정본 Modal 규격과 맞지 않음
- 회원가입·아이디/비밀번호 찾기 상세 흐름(보조 링크는 진입점만 제공)
